## 💼 Valor de negócio

O painel (Vercel) sobe no merge. A API (Railway) é deploy separado, manual. Entre um e outro existe uma janela em que **o web pede coisas que a API ainda não sabe responder** — e o projeto já pagou por essa janela três vezes:

| Quando | Como apareceu | Custo |
|---|---|---|
| Story 18.60 → 18.61 | "LP Paga zerada" — números certos lidos como bug de cálculo | investigação de código que estava correto |
| Story 29.43 (AC0) | 602 criativos gravados por dia, 0 com link | story bloqueada por 2 dias, duas re-medições em produção |
| 2026-08-10 | gráficos sumidos + "causa não determinada" na tabela de LP | nova investigação, esta story |

Em nenhuma das três a tela disse a verdade simples: *"o servidor está atrás do painel"*. O sistema **tem** essa informação nos dois lados e não a cruza em lugar nenhum.

O custo não é o deploy atrasado — é o tempo gasto procurando um bug de cálculo que não existe.

---

## 🔍 Diagnóstico (verificado na `main` e em produção, 2026-08-10)

### Como o sintoma chega hoje ao gestor

A ocorrência de 2026-08-10, na tabela "Desempenho por LP":

> *Causa não determinada: a API não informou o estado do cache — provável versão desatualizada. Rode o sync de criativos e confira novamente.*

Duas observações sobre essa frase (`perpetual-dashboard.tsx:2539-2547`):

1. **O diagnóstico está certo** — a 29.43 previu o cenário e o codificou honestamente. `perpetual-lp-rows.ts:135` só conta `causaIndeterminada` quando a resposta de `/ad-link-urls` **não traz** `staleInCache`, campo que a API na `main` sempre devolve (`traffic-analytics.ts:845`). É prova, não suspeita.
2. **A ação sugerida está errada** — "rode o sync de criativos" não conserta uma API defasada. O gestor executaria o sync, nada mudaria, e a confiança na mensagem cairia.

Ou seja: cada recurso novo precisa **redescobrir sozinho** que a API está atrás, e cada um erra de um jeito diferente. A 29.42 nem tentou — sumiu (é o que a 29.45 conserta).

### O que já existe e pode carregar o contrato

| Peça | Onde | Estado |
|---|---|---|
| Endpoint público, sem auth | `packages/api/src/routes/health.ts:5` (`/api/health`) | **pronto** — responde `200 {status, db, timestamp}`; verificado em produção em 2026-08-10 12:09 UTC |
| Bypass explícito de autenticação | `packages/api/src/middleware/auth.ts:10` | pronto — o web pode consultar antes de qualquer token |
| Pacote compartilhado pelos dois lados | `packages/shared` (`@loyola-x/shared`, dependência de web **e** api) | pronto |
| Commit do deploy | `RAILWAY_GIT_COMMIT_SHA` (API) · `VERCEL_GIT_COMMIT_SHA` (web) | disponível no ambiente, não exposto |

**Nada de infraestrutura precisa ser criado.** O que falta é um número e uma comparação.

### Por que não comparar commits

SHA não é ordenável: `a1b2c3` vs `d4e5f6` não diz quem é mais novo. Serve para **relatar** ("API em `0489cfe`"), não para **decidir**. A decisão precisa de um inteiro monotônico.

## 📖 Story

**Como** gestor de tráfego (e como o dev que atende o chamado dele),
**quero** que o painel avise, em uma frase, quando estiver rodando à frente da API,
**para que** o sintoma vire "falta deploy" em cinco segundos, em vez de virar uma investigação de bug inexistente.

## ✅ Critérios de aceite

### AC1 — Um contrato numérico, fonte única em `packages/shared`

`packages/shared/src/index.ts` exporta uma constante inteira monotônica:

```ts
/** Incrementar SEMPRE que o web passar a depender de algo que a API não tinha. */
export const API_CONTRACT_VERSION = 1;
```

Regra de uso, que vai no JSDoc da constante e é o coração da story: **quando um PR faz o web consumir um campo ou rota novos da API, esse mesmo PR incrementa o número.** Cada lado carrega a sua cópia compilada — a API publica a dela, o web compara com a dele — e a diferença revela a defasagem, nos dois sentidos.

Valor inicial: `1`. Não há tentativa de reconstruir retroativamente as versões passadas.

### AC2 — `/api/health` publica contrato e commit

`packages/api/src/routes/health.ts` passa a devolver, além do que já devolve:

```jsonc
{
  "status": "ok",
  "db": "connected",
  "timestamp": "…",
  "contract": 1,                 // API_CONTRACT_VERSION do shared
  "commit": "0489cfe"            // RAILWAY_GIT_COMMIT_SHA (7 chars) ou null
}
```

- Os campos existentes **não mudam** — há teste de contrato em `packages/api/src/__tests__/health.test.ts` e monitoria externa possível. *(Verificado na validação @po: aquele teste afirma campo a campo (`body.status`, `body.db`, `body.timestamp`), não `toEqual` estrito — acrescentar chaves não o quebra.)*
- `commit` é `null` quando a variável não existe (ambiente local). Ausência não é erro.
- O caminho de erro (`503`, DB fora) também devolve `contract` e `commit`: quando o banco cai, saber qual build está no ar é ainda mais útil.

### AC3 — O web compara e avisa uma vez, no topo

Hook novo (`useApiHealth` ou equivalente) consulta `/api/health` e compara `contract` com `API_CONTRACT_VERSION` do próprio bundle:

| Comparação | Significado | Tela |
|---|---|---|
| `api.contract < web.contract` | **API atrás** — o caso das três ocorrências | banner |
| `api.contract > web.contract` | web atrás (deploy da Vercel pendente) | banner com texto próprio |
| iguais, ou `contract` ausente na resposta | nada a dizer | silêncio |

Requisitos do banner:

- Aparece **uma vez por sessão**, no layout autenticado (`packages/web/app/(app)/layout.tsx`), não por seção — o problema é global.
  ⚠️ *Verificado na validação @po:* aquele layout é **Server Component** (sem `"use client"`), então o hook não pode ser chamado ali. O banner é um client component próprio, renderizado como filho — o mesmo arranjo que `Topbar` e `UserStatusGuard` já usam.
- Texto: qual lado está atrás, os dois números, e o commit da API quando houver. Ex.: *"A API está numa versão anterior à do painel (contrato 3 · painel 4 · API `0489cfe`). Alguns recursos podem não aparecer ou aparecer incompletos. Avise o time."*
- Dispensável pelo usuário na sessão (o gestor não pode ficar preso a um aviso que ele não resolve).
- **`contract` ausente na resposta não gera banner.** Uma API anterior a esta própria story não devolve o campo, e transformar isso em alarme faria a story disparar contra si mesma no dia do merge.

### AC4 — A tabela de LP para de sugerir a ação errada

`perpetual-dashboard.tsx:2539-2547`: quando `causaIndeterminada > 0`, a orientação deixa de ser "rode o sync de criativos" e passa a apontar a incompatibilidade de versão, alinhada ao banner do AC3.

A contagem e a classificação de `perpetual-lp-rows.ts` **não mudam** — o que muda é a frase de ação. A distinção das quatro causas da 29.43 continua exatamente como está.

### AC5 — Cobertura de teste

**API** (`vitest`, `packages/api/package.json:9`):
1. `/api/health` devolve `contract` igual a `API_CONTRACT_VERSION`
2. `commit` é `null` sem a env, e os 7 primeiros caracteres com ela
3. os campos `status`, `db` e `timestamp` seguem presentes (regressão do teste existente)

**Web** (`vitest`, `packages/web/package.json:10`), sobre a função pura de comparação. Ela **precisa** viver em `packages/web/lib/utils/` — `vitest.config.ts:33` só inclui `lib/utils/**/*.test.ts`, roda em `environment: "node"` e não tem `jsdom` nem `@testing-library`. Um teste em qualquer outro diretório simplesmente não é executado, e passa despercebido como verde:
4. `api < web` → veredito "API atrás"
5. `api > web` → veredito "web atrás"
6. iguais → sem banner
7. `contract` ausente/`undefined` → sem banner

## 📓 Notas para o @dev

- Comece pelo `shared` — os outros dois lados importam de lá; fazer o contrário cria dois números que já nascem podendo divergir.
- `/api/health` é público por bypass explícito (`middleware/auth.ts:10`): o hook do web pode consultá-lo antes do token do Clerk, e **deve** — a divergência de versão precisa ser detectável mesmo se a autenticação estiver quebrada.
- O @dev decide onde o banner vive; o AC3 fixa o comportamento, não o componente.
- Alternativa considerada e **rejeitada**: lista de `capabilities: string[]` em vez do inteiro. Mais expressiva e mais cara — exige que cada consumidor declare o que usa, e a dor medida (três ocorrências) é sempre a mesma: *a API inteira está atrás*. Se um dia a granularidade fizer falta, o inteiro não impede a evolução.

### ⚠️ Desvio do AC1, com motivo

A story mandava exportar a constante de `packages/shared/src/index.ts`. Implementado assim, **o `next build` quebrou**:

```
../shared/src/index.ts
Module not found: Can't resolve './types/funnel.js'
Import trace: ./components/layout/api-contract-banner.tsx
```

Causa: o índice do shared reexporta tipos com imports em estilo NodeNext, e o webpack do Next não resolve `.js` → `.ts`. Até aqui o web importava **apenas `import type`** do shared — apagado pelo compilador antes de qualquer resolução. Este é o primeiro import de **valor**, e por isso ninguém tinha esbarrado nisso.

Duas saídas foram consideradas:

1. `resolve.extensionAlias` no `next.config.ts` — conserta a classe inteira, mas mexe na resolução de módulos de **todo** o web para viabilizar uma constante. Risco desproporcional ao ganho, e num arquivo que ninguém revisaria com essa lente.
2. **Módulo folha** (escolhida) — `contract.ts` sem nenhum import, consumido pelo web via `@loyola-x/shared/src/contract`. O `index.ts` reexporta, então a API segue importando do índice e nada mais muda.

A opção 2 também é o desenho mais correto: uma constante de protocolo não deveria arrastar a árvore de tipos do domínio para ser lida. A fonte única — que era o ponto do AC1 — está preservada: um valor, um arquivo.
