## 📖 Contexto

A spec define duas tabelas de configuração que **não existem** no Loyola X (§1.5 `v_lancamento_config`, §1.6 `v_expert_config`) e um bloqueio obrigatório (§12.2) que impede o gerador de rodar em combinação nunca conferida.

### Mapeamento para o domínio real

A spec fala em "expert / projeto / etapa". No Loyola X:

| Spec | Loyola X |
|---|---|
| `expert` (dg, fz, bbe, pps) | `projects` (o cliente) — `schema.ts`, tabela `projects` |
| `projeto` / lançamento (pg02, pg04) | `funnels` — `funnels.matchCode` (`schema.ts:608`) já é a sigla usada pra casar campanha (ex.: `dg-pg02`) |
| `etapa` (`vendas-captacao`) | `funnel_stages` + `services/stage-phase.ts:22-42` (`resolveStagePhaseSuffix` já devolve `leads` \| `vendas-captacao` \| `vendas-principal`) |

### O que já existe e não deve ser duplicado

- **`produtos_order_bump`** já existe: `stageSalesSpreadsheets.orderBumpProducts` (`schema.ts:761`), jsonb de nomes de produto, match case-insensitive sobre `productName.trim().toLowerCase()`. A regra "todo produto NÃO listado aqui é captação" já está codificada em `stage-sales-data.ts:351-358`. **Não criar uma segunda lista.**
- **`imposto_pct`** já existe como constante global: `META_TAX_RATE = 0.1215` em `packages/api/src/utils/meta-tax.ts`, aplicada só a datas ≥ `2026-01-01`. A spec pede que seja **confirmável por expert** ("pode variar por regime tributário") — vira override opcional por projeto, com a constante como default.
- **`campos_pesquisa`** existe parcialmente: o `columnMapping` das pesquisas + a detecção de `faixa` já alimentam `computeSurveyForStage` (`survey-aggregation.ts:188`), que devolve `questions:[{key,label}]`. O que falta é o **mapa canônico** (`idade`, `renda`, `escolaridade`, …) que o bloco §4 do Resumão espera.

### O que falta de verdade

`tipo` (pago/gratuito/perpetuo), `etapa` normalizada, `entidade_captura` (vendas vs leads), `data_inicio`/`data_fim` explícitas, `validado`, override de `imposto_pct` por projeto, mapa de campos canônicos da pesquisa por projeto — e o **gate** que usa tudo isso.

## 🗳️ Decisões de escopo

| Dúvida | Decisão |
|--------|---------|
| Tabela nova ou colunas em `funnel_stages`? | **Tabela nova** `launch_report_configs` (1 linha por stage) + `expert_report_configs` (1 linha por projeto). `funnel_stages` já tem 20+ colunas de features distintas; misturar config de relatório ali piora a leitura e acopla o epic ao resto. |
| Duplicar `orderBumpProducts` na config? | **Não.** A config **referencia** a planilha do stage. `produtos_captacao` é derivado (todo produto que não é bump), exatamente como `stage-sales-data.ts:351-358` já faz. O invariante A8 (§8.1) roda em 41.3 sobre esse derivado. |
| `validado` default | **`false`.** Toda linha nova nasce bloqueada. Sair de `false` é ação humana explícita depois do checklist §12.7 — não é efeito colateral de salvar a config. |
| Quem pode marcar `validado = true`? | Equipe interna (mesma regra dos endpoints internos: `request.userRole === "guest"` → 403, padrão de `sprint-reports.ts:62`). Sem gate de admin dedicado nesta story. |
| Combinação DG/pago/captação já vem validada? | **Não por migration.** A migration cria as tabelas vazias; a config dos dois lançamentos da §10 é preenchida pela UI e marcada como validada só depois da conferência de 41.5/41.6. Seed que já nasce `validado=true` derrotaria o propósito do gate. |
| `data_inicio`/`data_fim` obrigatórias? | **Opcionais.** Nulo → derivar em 41.2 conforme §2.8 (início = 1ª venda/lead; fim = último dia com spend > 0). A regra de "não incluir wave 1" existe por causa de um caso real (FZ: R$ 1.130 de spend antes do 1º lead). |

## ✅ Acceptance Criteria

**AC1 — Schema de configuração**
**Given** a migration `0086_launch_report_configs.sql`, **when** aplicada, **then** existem duas tabelas:

- `launch_report_configs` — `id`, `stage_id` (FK `funnel_stages`, ON DELETE CASCADE, **UNIQUE**), `tipo` (`pago`\|`gratuito`\|`perpetuo`), `etapa` (varchar, um dos prefixos do §2.2), `entidade_captura` (`vendas`\|`leads`), `data_inicio` (date, nullable), `data_fim` (date, nullable), `imposto_pct` (numeric, nullable — override), `validado` (boolean NOT NULL DEFAULT false), `validado_em`, `validado_por` (FK `users`, ON DELETE SET NULL), timestamps.
- `expert_report_configs` — `id`, `project_id` (FK `projects`, CASCADE, **UNIQUE**), `imposto_pct` (numeric, nullable), `campos_pesquisa` (jsonb, default `{}` — mapa `campo_canônico → chave da pergunta`), timestamps.

O schema Drizzle em `packages/api/src/db/schema.ts` reflete as duas com os `$type<>` corretos, e a migration é reversível (DROP das duas tabelas).

**AC2 — CRUD interno**
**Given** um usuário interno (não-guest), **when** ele chama os endpoints da etapa, **then** consegue ler e gravar a config:
- `GET /api/projects/:projectId/funnels/:funnelId/stages/:stageId/report-config` → config do stage + config do expert (projeto) + `resolvido` (imposto efetivo = override do stage ?? override do projeto ?? `META_TAX_RATE`).
- `PUT .../report-config` → grava/atualiza (upsert por `stage_id`). **Alterar `tipo`, `etapa` ou `entidade_captura` reseta `validado` para `false`** — mudou a premissa, a conferência não vale mais.
- `POST .../report-config/validate` → marca `validado = true`, grava `validado_em`/`validado_por`.
- `PUT /api/projects/:projectId/report-config` → config do expert (imposto + `campos_pesquisa`).

Guest recebe 403 em todos (padrão `sprint-reports.ts:62`).

**AC3 — Gate de combinação não validada (§12.2)**
**Given** um helper exportado `assertReportScope(cfg)` em `packages/api/src/services/launch-report-config.ts`, **when** `cfg.validado === false` **e** (`cfg.tipo !== "pago"` **ou** `cfg.etapa !== "vendas-captacao"`), **then** ele lança/retorna erro que o caller traduz em **HTTP 422** com corpo exato:

```json
{
  "erro": "COMBINACAO_NAO_VALIDADA",
  "detalhe": "expert={projectName} tipo={tipo} etapa={etapa} — a spec foi validada para pago/vendas-captacao",
  "acao": "Preencher a configuração e rodar conferência manual contra o painel antes de liberar este botão"
}
```

**When** `validado === true`, **then** passa independente de tipo/etapa (o time assumiu a conferência). **When** não existe config para o stage, **then** 422 com `COMBINACAO_NAO_VALIDADA` e detalhe apontando a ausência — nunca assumir default.

**AC4 — UI de configuração na etapa**
**Given** uma etapa de funil de lançamento, **when** o usuário abre o Sheet **"Configurações da Etapa"** (gatilho `Settings2` em `.../stages/[stageId]/page.tsx:189-407` — é um `Sheet`, **não** uma aba), **then** vê um bloco "Relatórios (Resumão / Comparativo)" com: tipo, etapa, entidade de captura, período (início/fim, opcionais, com o texto explicando que vazio = derivado), override de imposto, e o **status de validação** — badge vermelho `Não validado — botões bloqueados` ou verde `Validado em {data} por {usuário}`, com o botão "Marcar como validado" acompanhado do checklist §12.7 renderizado como lista de conferência.

A lista de produtos (captação vs order bump) é **exibida em leitura** a partir de `stageSalesSpreadsheets.orderBumpProducts`, com link para o wizard existente — não é editável aqui (evita duas fontes de verdade).

**AC5 — Mapa de campos da pesquisa**
**Given** a config do expert, **when** o usuário edita `campos_pesquisa`, **then** ele escolhe, para cada campo canônico (`faixa` obrigatório; `idade`, `sexo`, `estado_civil`, `escolaridade`, `renda`, `profissao`, `setor`, `funcionarios`, `religiao` opcionais), qual das perguntas retornadas por `computeSurveyForStage` (`questions:[{key,label}]`) corresponde. Campo canônico não mapeado é simplesmente omitido do Resumão (§12.4) — não vira erro.

**AC6 — Gates**
`@loyola-x/api tsc --noEmit` verde para os arquivos desta story; `@loyola-x/web tsc --noEmit` + `next build` verdes. Migration aplicada em dev sem erro e revertida com sucesso ao menos uma vez.

## 📊 Complexidade & Valor

- **Estimativa:** **M.** Duas tabelas simples, CRUD no padrão já repetido no repo, uma UI de formulário. A parte que exige cuidado é o gate: precisa ser um helper único, testável e chamado por **todos** os endpoints do epic — não uma checagem copiada em cada rota.
- **Valor:** **Alto e defensivo.** Sem esta story, as 5 seguintes produzem número confiável só por acidente de quem clicou. O gate é o que impede o Resumão de sair errado para FZ/BBE parecendo certo.

---

## ⚠️ Riscos

- **R1 (médio) — Gate contornado por esquecimento.** Se 41.5/41.6 chamarem o motor sem passar por `assertReportScope`, o bloqueio vira decorativo. **Mitigação:** o gate mora **dentro** do carregador de config (`loadReportConfig` devolve config já validada ou lança) — não há caminho que carregue config sem passar por ele. Cobrir com teste.
- **R2 (médio) — `validado` virar carimbo automático.** **Mitigação:** default `false` na coluna, reset em toda mudança de premissa (AC2), e o checklist §12.7 renderizado na UI no momento de validar (AC4).
- **R3 (baixo) — Divergência de imposto.** Override por projeto pode ser preenchido errado e passar despercebido. **Mitigação:** `GET` devolve `resolvido` mostrando de onde veio o valor efetivo (stage / projeto / default), exibido na UI.
