## Story

Como quem vai montar um dashboard, quero **escolher métricas e dimensões de uma lista com nome em português**, para não precisar saber o nome da coluna no banco nem qual tabela tem o quê.

Sem isto, o editor de widget não tem o que oferecer e o executor de query não tem como validar o que recebeu.

## Contexto

O dossiê chama isto de `GET /api/mcp/semantic-labels` e é explícito: *"Sem isso o editor não funciona"* (passo 3 da Fase 0).

O catálogo é a **fronteira de segurança** da feature: o executor só aceita métrica e dimensão que existam aqui. Um campo que não está no catálogo não é consultável — é o que impede uma query de alcançar coluna arbitrária.

## Contexto Técnico

### As entidades reais deste app

Não são as 7 do VK. São as que o Loyola X tem:

| Entidade | De onde vem | Grão |
|---|---|---|
| `trafego` | `meta_ads_daily_metrics` (cache Meta) | dia × campanha × conjunto × criativo |
| `vendas` | planilha de vendas + `manual_sales` | transação |
| `aplicacoes` | planilhas de aplicação (ao vivo) | resposta de formulário |
| `grupos` | `funnel_group_snapshots` (SendFlow) | dia × campanha |
| `custos` | custos operacionais da etapa | lançamento |

⚠️ `aplicacoes` é lida **ao vivo da planilha**, não do banco. O executor precisa tratar essa entidade por outro caminho — ver 45.2.

### Forma de cada campo

```ts
{
  key: "trafego.spend",
  label: "Investimento",
  entity: "trafego",
  role: "metric",             // metric | dimension
  semanticType: "currency",   // currency | number | percent | date | text
  aggregation: "sum",         // sum | avg | count | count_distinct | none
  dataType: "number",
  /** Fórmula, quando a métrica é derivada de outras. */
  formula?: "spend / leads",
  /** O que o número responde — vira tooltip no editor. */
  description: "Quanto foi gasto em mídia paga no período",
}
```

### Métricas com família (regra 5 do épico)

`ROAS (Geral)` e `ROAS (Atribuído)` são **duas entradas** no catálogo, com `key` diferente e o rótulo dizendo qual é. Nunca uma só.

## Critérios de aceitação

**AC1** — `GET /api/bi/catalogo` devolve `{ metrics: [], dimensions: [] }` com todos os campos acima, e é acessível a qualquer usuário não-guest.

**AC2** — O catálogo é **declarado em código** (`packages/api/src/services/bi/catalogo.ts`), não montado por introspecção do banco. Introspecção exporia coluna interna e mudaria de forma a cada migration.

**AC3** — Toda métrica de taxa tem `null` como resultado sem denominador, e isso está declarado no catálogo (`nullWhenEmpty: true`).

**AC4** — Métricas com duas famílias aparecem como duas entradas, com rótulo distinto. Um teste garante que não existe métrica de atribuição sem o par.

**AC5** — `GET /api/bi/valores?entity=&dimension=&search=&limit=` devolve os valores distintos de uma dimensão, para o autocomplete de filtro. Limite máximo 100, busca case-insensitive.

**AC6** — Toda chave do catálogo é única. Teste que falha com chave duplicada.

## Testes

| # | Verifica |
|---|---|
| T1 | Nenhuma chave duplicada no catálogo |
| T2 | Toda métrica tem `entity` que existe na lista de entidades |
| T3 | Métrica de taxa declara `nullWhenEmpty` |
| T4 | Para toda métrica `*_atribuido` existe a `*_geral` correspondente |
| T5 | `/valores` respeita o limite e não aceita dimensão fora do catálogo (400) |

- [ ] Dimensões: data, campanha, conjunto, criativo, origem, produto, etapa
- [ ] `tsc` limpo, testes passando
- [ ] Nenhuma consulta ao banco no endpoint de catálogo (é estático)
