## 💼 Valor de negócio

As stories 29.35, 29.36 e 29.37 foram mergeadas na `main` e **nenhuma delas funciona**. O usuário reportou dois sintomas; ambos são a mesma doença:

> *"em Premissas do Produto → está com erro ao salvar premissas"*
> *"Tento selecionar alguma arquitetura do funil e dá erro Não foi possível salvar"*

Três semanas de trabalho entregues e inutilizáveis. Esta story não adiciona funcionalidade — **liga** o que já foi construído.

## 🔍 Diagnóstico (feito, não suposto)

### Causa 1 — as migrations nunca foram aplicadas

Consulta ao banco de produção (`187.77.231.80:5433/postgres`) em 2026-08-05:

```
margem_desejada_pct   FALTA
cmv                   FALTA
gateway_fixo          FALTA
funnel_architecture   FALTA
chain_defect_reading  FALTA
manual_rates          FALTA
ceilings              FALTA
```

**As 7 colunas do Epic 29 não existem.** Toda escrita da aba MVP bate em `42703 column does not exist` → 500 → o `catch` do front mostra "Não foi possível salvar". As leituras (`GET`) também falham, e como o componente descarta `isError`, a aba aparece vazia em vez de mostrar erro — o usuário conclui que nunca salvou nada.

Isto é o item **B1** da auditoria de 2026-08-04, que foi registrado como bloqueante e nunca executado.

E há um agravante descoberto em 2026-08-05: a `origin/main` ganhou uma **segunda** migration `0092` (a do VTurb, PR #469), que **foi** aplicada. Duas migrations disputando o mesmo número na mesma pasta — daí o AC1.

### Causa 2 — o upsert apaga tudo que o PUT não manda (bug latente, pior que o primeiro)

`packages/api/src/routes/perpetual-report-config.ts:237-260`. O `PUT` foi desenhado na 41.7 para **substituição total**: a tela de config manda o formulário inteiro. Os campos usam `d.x ?? null`.

A aba MVP **não** manda o formulário inteiro — manda só o que ela edita (`{ funnelArchitecture }` ou `{ margemDesejadaPct, cmv, gatewayFixo }`). Resultado, no primeiro salvamento bem-sucedido:

| Campo | Vira | Consequência |
|---|---|---|
| `prefixoCampanha` | `null` | escopo de campanhas do relatório se perde |
| `produto` / `produtosOrderBump` | `null` / `[]` | vendas deixam de ser filtradas por produto |
| `inicioTrafego` | `null` | — |
| `impostoPct` | `null` | **imposto some do cálculo** |
| `taxaPlataformaPct` / `taxaImpostoPct` / `taxaOutrosPct` | `null` | **líquido passa a ser igual ao bruto** |
| `temSplitFormato` / `origensPagas` | `false` / `["meta"]` | premissa silenciosamente trocada |
| `margemDesejadaPct` / `cmv` / `gatewayFixo` | `null` | **apaga o que a outra seção da própria aba acabou de salvar** |

E como `prefixoCampanha` e `impostoPct` mudaram, `premissaMudou` (`:220`) fica `true` → **`validado` é resetado para `false`** → o gate do §C.8 **bloqueia o relatório perpétuo inteiro**.

Ou seja: aplicar as migrations sem corrigir isto troca um erro visível por uma **destruição silenciosa de configuração**. As duas causas têm que ser resolvidas na mesma entrega.

O comentário que eu mesmo deixei na `:253` descreve exatamente este problema — mas a proteção foi aplicada só aos 4 campos novos, e não aos 11 originais.

### Causa 3 — o front esconde a causa

`perpetual-mvp-analysis.tsx` tem três `} catch {` sem parâmetro e sem log, e descarta o `isError` da query de config. Se qualquer um deles registrasse o status HTTP, este diagnóstico teria custado 30 segundos em vez de uma investigação no banco. É o item **B4** da auditoria.

## ✅ Critérios de aceite

### AC1 — Resolver a colisão de número `0092`

A `origin/main` tem **duas migrations `0092`**: a minha (`0092_perpetual_target_cac_inputs`) e a do VTurb (`0092_vturb`, PR #469) — e **a do VTurb já foi aplicada** (`vturb_connections` existe no banco com 1 conexão ativa).

- Renumerar as três do Epic 29 para os próximos números livres, preservando a ordem relativa:
  `0092_perpetual_target_cac_inputs` → **`0095`**
  `0093_perpetual_manual_rates` → **`0096`**
  `0094_perpetual_ceilings` → **`0097`**
- As três só tocam `perpetual_report_configs` com `ADD COLUMN IF NOT EXISTS`, sem dependência entre si — renumerar não muda comportamento.
- **Não** renomear a `0092_vturb`: já foi aplicada e é a que tem posse legítima do número.
- `drizzle.__drizzle_migrations` está **vazia** — não há ledger a atualizar. As migrations deste projeto são aplicadas à mão (padrão `packages/api/migrate-00XX.ts`), o que torna a renumeração segura.

### AC2 — Migrations aplicadas em produção, com evidência

As três renumeradas, aplicadas **nesta ordem**, no banco de produção.

- Evidência obrigatória na story: saída de `information_schema.columns` listando as 7 colunas **presentes**.
- Todas são `ADD COLUMN IF NOT EXISTS` — reexecutar é seguro.
- **Ordem importa em relação ao deploy:** as migrations vão **antes** do deploy da API. O inverso (API nova, banco velho) é exatamente o estado quebrado de hoje.

**Decisão do @po (2026-08-05) — a coluna do gateway já nasce percentual.** A `0095` cria **`gateway_pct_var numeric(6,5)`** (fração) e **não** cria `gateway_fixo`.

Motivo: a 29.39 aprovada troca essa mesma coluna, e a coluna nunca existiu em lugar nenhum — criar `gateway_fixo` agora para removê-la na próxima story seria escrever uma migration cujo único efeito é ser desfeita. Isto desfaz também a dependência circular que existia entre as duas stories (esta esperava a decisão da 29.39, e a 29.39 declarava depender desta).

Consequência para o escopo desta story: o `configBodySchema` e o `values` do PUT usam `gatewayPctVar` desde já. A **fórmula**, o rótulo da UI e o teste de paridade continuam sendo escopo da 29.39 — aqui é só schema, para que a 29.39 não precise de migration própria.

### AC3 — O PUT preserva todo campo que não vier no corpo

Todos os campos de `values` (`:237-260`) seguem a mesma regra, sem exceção:

```ts
campo: d.campo !== undefined ? <transformação> : (existing?.campo ?? <default do INSERT>)
```

- Vale para os 11 campos originais **e** para os 4 da 29.36/29.37.
- `undefined` (não mandou) e `null` (mandou vazio de propósito) continuam sendo coisas diferentes — `null` **limpa** o campo, e isso é comportamento correto que deve ser preservado.
- No INSERT (`existing == null`) os defaults atuais valem: `[]`, `false`, `["meta"]`, `null`.
- Refatorar para um helper em vez de repetir o ternário 15 vezes — o padrão repetido é como o bug entrou.

### AC4 — Salvar da aba MVP não reseta `validado`

`premissaMudou` já ignora campo `undefined` nos helpers `fieldChanged`/`numericChanged`. Com o AC3 aplicado isso passa a valer de fato.

- **Teste obrigatório:** config com `validado = true` + `PUT { funnelArchitecture: "vsl_direct" }` → resposta traz `validadoResetado: false` e a linha continua `validado = true`.
- O mesmo para `PUT { margemDesejadaPct, cmv, gatewayPctVar }`.

### AC5 — A aba MVP mostra o erro real

Nenhum `} catch {` sem parâmetro no componente.

- Toast informa a causa quando a API devolve uma: status + mensagem do corpo. `"Não foi possível salvar"` puro fica só como último recurso, quando não há nada mais específico.
- O `isError` da query de config vira estado visível na aba — hoje é descartado, e erro de carga é indistinguível de "ainda não configurou".
- Detalhe técnico (status, corpo) vai para `console.error`; o toast fica legível para o usuário.

### AC6 — Testes de regressão do PUT parcial

Em `packages/api/tests/`, cobrindo o cenário que produziu o bug:

1. Config completa (prefixo, produto, 4 taxas, `validado = true`) + `PUT { funnelArchitecture }` → **os 11 campos originais intactos**, arquitetura gravada, `validado` intacto.
2. Config completa + `PUT { margemDesejadaPct, cmv, gatewayPctVar }` → idem, e `manualRates`/`ceilings` intactos.
3. `PUT { prefixoCampanha: null }` → o prefixo é **limpo** (distinção `null` vs `undefined` preservada).
4. INSERT (sem config prévia) com corpo parcial → defaults corretos, sem erro.
5. `PUT` completo pela tela de config antiga → comportamento inalterado (não-regressão da 41.7).

### AC7 — Validação end-to-end na aplicação real

Depois do deploy, com evidência na story:

- Salvar Premissas do Produto → sucesso, valores persistem após F5.
- Selecionar uma arquitetura → sucesso, seleção persiste após F5.
- Abrir a tela de config do relatório (botão 3) → prefixo, produto e as 4 taxas **inalterados**; `validado` inalterado.
- Relatório perpétuo abre normalmente (gate §C.8 não bloqueou).

Isto cobre também **B2/B3** da auditoria: 29.35/29.36/29.37 nunca foram validadas visualmente porque nunca puderam ser.

### AC8 — Registro do que ficou pendente

Atualizar `docs/stories/29.35/29.36/29.37` com o motivo real da não-validação (banco sem as colunas) e apontar para esta story. Sem isso, o histórico sugere que foram validadas e não foram.
