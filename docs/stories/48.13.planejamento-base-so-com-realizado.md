## 💼 O pedido e o que o levantamento mostrou

**Medido em produção em 2026-09-23 (SELECT, funil `fz-m3-set-26`, `66aa4c1f…`, projeto FZ & MFB `4d7f55ea…`):**

- O sistema **reconhece** `fz-m1-mai26` e `fz-m2-jul26` como meteóricos anteriores — `lancamentosAnteriores` devolve `['fz-m2-jul26', 'fz-m1-mai26']`. **Estar arquivado não atrapalha:** `funisDeLancamento` (`planejamento-repositorio.ts:498-516`) filtra só por projeto e `type = 'launch'`, sem `archived_at`.
- Eles caem no filtro `.filter((a) => porId.get(a.id)?.temSimulador)` (`routes/planejamento.ts:459`): a regra da 48.9 (AC2) só oferece como base quem **já tem simulador salvo**, e no sistema inteiro **só o fz-m3 tem** (a única linha de `plan_simulators`). Não é erro virando ausência: a frase só aparece com a resposta de `/bases` bem-sucedida (`page.tsx:190-197`).
- O **realizado** desses dois lançamentos existe (Story 48.11): fz-m1 R$ 4.022,04 de investimento Meta (01/05 → 17/05, 2 campanhas, etapa Vendas); fz-m2 R$ 7.574,19 (27/07 → 08/08, 4 de 5 campanhas, etapas Vendas e Downsell). Hoje ele só aparece depois de escolher uma base — e a base nunca aparece porque falta o simulador.

**Decisão do Danilo (2026-09-23): opção B** — lançamento anterior do mesmo tipo **sem** Planejamento salvo passa a ser oferecido como base, e a tela mostra **só o `real:`** dele. É o que dá ao fz-m3 o histórico real do fz-m1 e do fz-m2 sem ninguém preencher simulador retroativo.

**Bug lateral (2.4):** a rota calcula o tipo do **próprio** funil como `anteriores[0]?.tipo ?? null` (`routes/planejamento.ts:457`). Num funil que é o **primeiro do seu tipo** (ex.: `fz-l2-jun-26`, gratuito sem gratuito anterior), sai `tipo: null` e a tela diz "o nome deste funil não identifica o tipo de lançamento" — o que é falso. O teste "primeiro do tipo → sem base" não confere o `tipo`.

## ✅ Acceptance Criteria

- **AC1** — `GET …/planejamento/bases` passa a devolver **todos** os lançamentos anteriores do mesmo projeto e tipo (a regra de casamento da 48.9 AC1 não muda), **com e sem** simulador salvo. Cada item ganha `temSimulador: boolean`; `simuladorAtualizadoEm` fica `null` quando não há simulador. Ordem igual à de hoje (do mais recente para o mais antigo). Funis arquivados continuam entrando.
- **AC2** — O `tipo` da resposta é o do **próprio funil**, calculado a partir do nome dele (`identificarLancamento(alvo.nome).tipo`), **não** do primeiro anterior. Consequência testada: `fz-l2-jun-26` (primeiro gratuito) devolve `tipo: 'l'` com `bases: []`; `bbe-web-mai-26` (pedaço `web` fora do dicionário) continua `tipo: null`.
- **AC3** — Frase quando não há base, por motivo:
  - `tipo === null` → a frase atual ("…o nome deste funil não identifica o tipo…");
  - `tipo !== null` e nenhum anterior → **"Sem histórico anterior — este é o primeiro {rótulo do tipo} deste expert."**, com o rótulo de `rotuloDoTipoDeLancamento(tipo)` (shared): "…o primeiro **lançamento gratuito** deste expert", "…o primeiro **meteórico**…", "…o primeiro **lançamento pago**…", "…o primeiro **evento presencial**…". *(PO-02: o rascunho dizia "primeiro lançamento {rótulo}", e os rótulos já trazem "lançamento" — sairia "primeiro lançamento lançamento gratuito", contra o próprio DoD.)*
  - com a **API nova**, a frase "nenhum lançamento anterior do mesmo tipo tem o Planejamento preenchido" deixa de aparecer (com a API antiga, ver AC7).
- **AC4** — No seletor "Selecionar campanha anterior…", a base sem simulador aparece identificada como tal (ex.: `fz-m2-jul26 · meteórico · só realizado`). A base com simulador aparece como hoje.
- **AC5** — Escolhida uma base **sem** simulador:
  - **nenhum `base:`** aparece em campo nenhum (as leituras de inputs/orgânicos/pagos da base não são usadas — valor padrão ou vazio de um simulador inexistente **não** pode virar referência);
  - o `real:` aparece como na 48.11 (investimento, % quente, ticket médio, conversão por canal) — rótulo no formato `(real: Y)`;
  - o cabeçalho da base diz, em uma linha, que esse lançamento não tem Planejamento salvo e por isso só o realizado aparece, **junto** da declaração de cobertura que a 48.11 (AC8) já mostra.
- **AC6** — Escolhida uma base **com** simulador: comportamento idêntico ao de hoje (`base:` + `real:`).
- **AC7** — **Front não pode exigir API nova** (29.45/18.60): API antiga (sem `temSimulador`) → a tela trata toda base recebida como "com simulador", exatamente como hoje, sem erro. **`API_CONTRACT_VERSION` sobe uma versão** (19 → 20, ou a seguinte, se outra story subir antes do merge).
  - **Lista vazia com a API antiga** *(PO-03)*: a API antiga filtra os anteriores sem simulador, então para o `fz-m3-set-26` ela devolve `{ tipo: 'm', bases: [] }` — e a frase nova do AC3 afirmaria **"primeiro meteórico deste expert"**, o que é falso (existem `fz-m1` e `fz-m2`). Com `bases: []` não há item onde procurar `temSimulador`; por isso a **resposta nova carrega um sinal no nível de cima** (não só nos itens) de que a lista inclui os anteriores sem simulador. **Sem esse sinal**, lista vazia mantém a frase de hoje ("…nenhum lançamento anterior do mesmo tipo tem o Planejamento preenchido") — que é verdadeira sob a regra antiga. O nome e a forma do sinal ficam com o @dev.
- **AC8** — Testes, cada um com prova diferencial (mutação tem de derrubar):
  - rota: anterior **sem** simulador agora **aparece** com `temSimulador: false` (inverte o teste "anterior sem simulador é omitido" da 48.9 — declarar a inversão no teste);
  - rota: `tipo` do primeiro do tipo é o do próprio funil (volta a `anteriores[0]?.tipo` → falha);
  - web (`lib/utils`): base sem simulador → nenhuma referência `base:` mesmo recebendo inputs com valores; com simulador → referência como hoje; frase por motivo (os dois casos do AC3) **e o caso da API antiga do AC7** (`bases: []` + `tipo` não nulo + sem o sinal → frase de hoje, nunca "primeiro…"); *(PO-03)*
  - fixture com os nomes reais: `fz-m3-set-26` → `fz-m2-jul26`, `fz-m1-mai26` (ambos sem simulador).
- **AC9** — Gates: eslint 0 **nos arquivos tocados** — o erro herdado da `main` em `packages/api/src/routes/sendflow.ts:39` (`'SendflowRelease' is defined but never used`, medido em 2026-09-23) fica à parte, como o baseline do vitest *(PO-04)*; tsc shared/api/web 0 (depois do `next build`); `next build` EXIT 0; vitest verde (baseline conhecido da API à parte).
