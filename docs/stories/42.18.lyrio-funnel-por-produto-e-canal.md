## 💼 Contexto medido (2026-10-27, leitura do código; nenhum dado de produção foi consultado pelo @sm)

### 1. As taxas já existem, mas só por canal
`<LyrioJornadaPorCanal>` (42.11) tem uma linha por canal (+ Total), com Novos → Viu paywall → Interagiu → **Iniciou (teste)** → Pagou, a receita e as taxas contra Novos (`taxaDaJornada`). A coorte é o primeiro evento do usuário na janela do filtro.

As regras (`packages/api/src/utils/jornada-lyrio.ts:186-189`):
- **iniciou** = algum `INITIAL_PURCHASE` ou `NON_RENEWING_PURCHASE`, com qualquer `period_type`;
- **iniciou_teste** = algum `INITIAL_PURCHASE` com `period_type = 'TRIAL'`.

### 2. "Por produto" hoje é outra coisa
O "Por produto" do painel RevenueCat do rodapé (`RevenuecatPanel`, `byProduct` de `/revenuecat/sales`) conta **vendas pagas na janela** por `product_id` (top 20). Ele mede eventos, não coorte. Pôr uma taxa de coorte nessa tabela misturaria duas réguas.

### 3. O "Novo" não tem produto
Um usuário novo só ganha `product_id` quando inicia um teste ou uma compra. Quem não iniciou não tem produto. Então **o denominador de Novos → X é o canal, não o produto**:

> taxa(produto P, canal C) = usuários novos do canal C cuja primeira compra/teste foi P ÷ novos do canal C

A soma das taxas dos produtos de um canal é a taxa do canal que a Jornada já mostra. Isso dá uma prova de paridade (AC4c).

### 4. A classificação de produto já existe (42.14)
`classificarProduto` (`pagantes-lyrio.ts:231`) leva os `product_id` (famílias `premium_*` e promoções `rc_promo_Lyrio Pro_*`, D33 da 42.14) a **Mensal / Trimestral / Semestral / Anual / fora / não classificado**, com a equivalência TS × SQL provada no PGlite (`classeDoProdutoNoSql`).

SQL do AC1 (parâmetros à parte; `$1` = etapa, `$2` = `'TEST'`, `$3` = início da janela, `$4…` = os prefixos e nomes da classificação da 42.14):
```sql
WITH u AS (
  SELECT (array_agg(product_id ORDER BY event_at, product_id COLLATE "C" NULLS LAST)
            FILTER (WHERE event_type IN ('INITIAL_PURCHASE','NON_RENEWING_PURCHASE')))[1] AS p_ini,
         (array_agg(product_id ORDER BY event_at, product_id COLLATE "C" NULLS LAST)
            FILTER (WHERE event_type = 'INITIAL_PURCHASE' AND payload->'event'->>'period_type' = 'TRIAL'))[1] AS p_tes,
         coalesce(bool_or(event_type IN ('INITIAL_PURCHASE','NON_RENEWING_PURCHASE')), false) AS iniciou,
         coalesce(bool_or(event_type = 'INITIAL_PURCHASE' AND payload->'event'->>'period_type' = 'TRIAL'), false) AS teste
  FROM revenuecat_sales
  WHERE stage_id = $1 AND app_user_id IS NOT NULL AND event_type <> $2
  GROUP BY app_user_id HAVING min(event_at) >= $3::timestamptz)
SELECT 'iniciou', CASE WHEN p_ini IS NULL THEN 'sem_produto' ELSE <classeDoProdutoNoSql(p_ini)> END, p_ini, count(*)
FROM u WHERE iniciou GROUP BY 2, 3
UNION ALL SELECT 'teste', CASE WHEN p_tes IS NULL THEN 'sem_produto' ELSE <classeDoProdutoNoSql(p_tes)> END, p_tes, count(*)
FROM u WHERE teste GROUP BY 2, 3
UNION ALL SELECT 'novos', 'coorte', NULL, count(*) FROM u;
```
A consulta entregue troca o `array_agg … ORDER BY` por um `min` sobre uma chave de ordem, com a mesma regra (ver AC3d). A conferência final (abaixo) roda o código entregue e chega à mesma distribuição.

### Decisões
- **[AUTO-DECISION] Empate no mesmo `event_at` (AC2a):** o evento COM `product_id` vence o sem; entre dois ids, vence o menor em bytes (`COLLATE "C"`). (Razão: a regra fica determinística e não depende da collation do banco; o nulo só vira "Sem produto" quando não há id nenhum no primeiro instante.) Testado na função pura e no PGlite.
- **Cada medida tem o seu primeiro evento:** o produto de Novos → Iniciou é o do primeiro `INITIAL_PURCHASE`/`NON_RENEWING_PURCHASE`; o de Novos → Trial, o do primeiro `INITIAL_PURCHASE` com `TRIAL`. É a leitura literal do AC2a.
- **[AUTO-DECISION] Arquivo novo `utils/jornada-por-produto-lyrio.ts` (IDS: CREATE):** `pagantes-lyrio.ts` já importa de `jornada-lyrio.ts`. Pôr `classeDoProdutoNoSql` dentro da Jornada fecharia um ciclo de módulos. A Jornada ganhou só o parâmetro `extras` em `consultaDaJornada`, para as colunas do produto entrarem na MESMA redução por usuário (AC3d). REUSE: `canalDoUsuario`, `CANAIS_DA_JORNADA`, `coorteDaJornada`/`escopoDaJornada`, `classeDoProdutoNoSql`, `classificarProduto`, `REGRA_DOS_PLANOS`; na web, `taxaDaJornada`, `formatarTaxa` e `estadoDoBlocoDaJornada`.
- **AC3d, desempenho (EXPLAIN ANALYZE em produção, 90 dias, PG 17.11):** com `(array_agg(product_id ORDER BY …))[1]`, o Postgres perde a agregação parcial nos workers: 3,83 s contra 1,47 s da consulta da `main`. Troquei por `min(chave COLLATE "C") FILTER (…)`. A chave é o instante em µs com 20 dígitos, `0` + id ou `1` sem id. Com ela, a agregação parcial volta: 1,81 s no EXPLAIN. Medido do cliente, 3 execuções cada: **90 dias, 1.617 / 1.730 / 1.539 ms, contra 1.521 / 1.779 / 1.485 ms da `main`**; 28 dias, 1.970 / 1.748 / 1.604 ms contra 1.700 / 1.470 / 1.600 ms. Limites declarados no código: o TS compara milissegundos (`Date`), e o banco, microssegundos; instante anterior a 1970 não ordenaria.
