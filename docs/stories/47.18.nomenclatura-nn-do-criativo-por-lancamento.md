## ✅ Acceptance Criteria

- **AC1 — Escopo do NN.** O NN do criativo é único por **(expert, sigla do lançamento, nº do lançamento, tipo de criativo)** — o lançamento é `{sigla}{NN}` (spec `:452`). Exemplos do pedido: no `pg01` convivem `ad01`, `ad02`, `adv01`, `adv02`; o `pg02` pode ter `ad01`, `ad02` de novo. Para `perpetuo` (nº do lançamento **ausente**, 47.16), a sequência é a do conjunto (expert, `perpetuo`, tipo) — ausente conta como **um** valor, não como "sempre diferente".
- **AC2 — Banco.** *(reescrito pelo @po — PO-01/PO-02)* Migration nova (próximo número livre pelo censo real de `packages/api/src/db/migrations/`; hoje a última é 0158) troca `uq_naming_ads_expert_seq` por uma garantia de unicidade **no banco** sobre `(expert_id, launch_type, launch_seq, creative_type, creative_seq)` em que `launch_seq` NULL conta como um valor (`NULLS NOT DISTINCT`, PG 15+; produção é 17.11). Três exigências:
  - **(a) A subida da API não desfaz nem refaz.** O CMD do container roda `drizzle-kit push --force` a cada boot (`packages/api/Dockerfile:26`). O `schema.ts` tem de declarar a garantia de um jeito que o push trate como **igual** ao que está no banco — nem recriar sem `NULLS NOT DISTINCT`, nem dropar e recriar a cada boot. Ver Dev Notes (PO-01) para o que foi conferido nas versões instaladas.
  - **(b) Idempotente pela definição, não pelo nome.** Rodar duas vezes é seguro, **e** se já existir um índice com o nome novo mas **sem** `NULLS NOT DISTINCT` (o push o cria assim se a API nova subir antes da migration), a migration o corrige. `CREATE UNIQUE INDEX IF NOT EXISTS <nome>` sozinho **não** serve.
  - **(c) Narrada, com a prova:** `SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'naming_ads'` — esperado: o índice novo com `NULLS NOT DISTINCT` nas 5 colunas e **nenhum** `uq_naming_ads_expert_seq`. Os 6 anúncios existentes continuam válidos (nenhuma colisão no escopo novo).
- **AC3 — Sugestão do próximo NN.** A rota do próximo NN e `montarAnuncio` passam a considerar só os anúncios do **mesmo** expert + sigla + nº + tipo. Com o formulário ainda sem tipo ou sem lançamento completo (sigla com número e sem o nº; `perpetuo` é completo só com a sigla), a tela diz o que falta em vez de sugerir número — e a sugestão do nº do lançamento (`launchSeqSugerido`, por expert + sigla) continua funcionando com o que já há. **A sigla `perpetuo` entra no escopo do NN** (PO-06: o `siglaParaSugestao` de hoje a omite de propósito — ele é da sugestão do nº do lançamento, não do NN). Exemplo de aceite: dg, `ad`, `pg05` → **01**; dg, `adv`, `perpetuo` → **07**.
- **AC3b — O NN acompanha o escopo.** *(novo, PO-06)* Trocar tipo, sigla ou nº do lançamento num anúncio **novo** não deixa no campo o NN sugerido para o escopo anterior: o NN é limpo e a sugestão do escopo novo o preenche (mesma regra de hoje ao trocar o expert). Exemplo: dg, `adv`, `perpetuo` (preenche 07) → trocar para `ad` + `pg05` → o campo mostra **01**, não 07.
- **AC4 — Colisão.** Gravar um NN já usado **no mesmo escopo** continua recusado com mensagem clara (409) que nomeia o **dono dentro do escopo** (PO-05: `porSeq` hoje procura só por expert e nomearia o anúncio errado), inclusive por corrida (violação do índice → 409, não 500 — o caminho genérico já existe; aqui é provar com o índice novo). O mesmo NN em outro lançamento ou outro tipo é aceito.
- **AC5 — Edição.** *(corrigido pelo @po — PO-04)* Trocar **sigla ou nº do lançamento** de um anúncio existente revalida o NN **no escopo novo** (PATCH). O tipo não muda na edição (D23 — o PATCH não aceita `creativeType`). Como o NN é fixo depois de salvo, a colisão no escopo novo é 409 que nomeia o dono e **não** oferece outro NN como saída; na tela de edição o 409 não troca o NN mostrado no formulário (hoje `gerador-de-anuncio.tsx:258` aplica `corpo.sugestao` sem olhar o modo).
- **AC6 — Texto da tela:** "Próximo livre de {expert} em {sigla}{nº} ({tipo}): NN" — com `perpetuo`, "em perpetuo ({tipo})" (sem número, 47.16). O texto "Sequência única por expert, qualquer tipo" sai.
- **AC7 — Contrato.** *(tornado incondicional pelo @po — PO-07)* A rota do próximo NN ganha parâmetros (tipo e nº do lançamento) e muda de significado ⇒ **`API_CONTRACT_VERSION` sobe** (hoje 27; o próximo livre no merge, com a linha de histórico) com fallback no web: com a API atrás, a tela **não** rotula com escopo um número que a API antiga calculou por expert (o `z.object` da rota antiga descarta os parâmetros novos em silêncio e devolveria 07 para `ad` + `pg05`).
- **AC8 — Testes** com prova diferencial, inclusive do fio: escopo da sugestão (o exemplo do AC3; voltar a `seqsDoExpert` sem filtro derruba); `perpetuo` com NULL no escopo (dois `adv01` perpetuo do mesmo expert colidem); mesmo NN em `pg01` e `pg02` aceito; mesmo NN em `ad` e `adv` do mesmo lançamento aceito; dono do 409 no escopo (AC4); PATCH que muda o lançamento para um escopo ocupado → 409 (AC5); troca de escopo limpa o NN (AC3b); `perpetuo` chega à rota do NN (AC3); predicado Drizzle renderizado com `PgDialect`; corrida → 409. Os testes que hoje fixam a regra antiga (`nomenclatura-rotas`, `nomenclatura-repositorio`, `nomenclatura-anuncio-nome`, e o regex do fio em `web/lib/utils/__tests__/nomenclatura-anuncio-fio.test.ts:23`) são **invertidos**, não apagados.
- **AC9 — Gates:** eslint 0 erro novo; tsc shared/api/web 0 (web depois do `next build`); `next build` EXIT 0; vitest verde (baseline da API à parte).

## 📝 Dev Notes

- **PO-01 — o que as versões instaladas aceitam (conferido em 69e75516):**
  - `drizzle-orm` 0.45.1: o `IndexBuilder` (`uniqueIndex(...).on(...)`) **não** tem `nullsNotDistinct()`; só o `unique()` de constraint tem (`pg-core/unique-constraint.d.ts:10`).
  - `drizzle-kit` 0.31.9: a introspecção de **UNIQUE constraint** grava `nullsNotDistinct: false` fixo (`bin.cjs` ~19566), e o `nullsNotDistinct` entra na comparação (`bin.cjs:6503`) ⇒ declarar `unique(...).nullsNotDistinct()` dá **diferença perpétua**: o `push --force` do boot faria DROP + ADD CONSTRAINT a cada subida (e, se falhar, a API não sobe — o CMD é `push && node`).
  - A introspecção de **índice** não lê `indnullsnotdistinct` (`bin.cjs` ~19703: `indisunique`, `indoption`, colunas) ⇒ um `uniqueIndex("<nome>").on(5 colunas)` no `schema.ts` + `CREATE UNIQUE INDEX … NULLS NOT DISTINCT` na migration é visto como igual pelo push. Esse é o caminho conferido; o @dev pode escolher outro desde que prove o AC2(a) (ex.: rodar `drizzle-kit push` sem `--force` contra o banco já migrado e mostrar "no changes").
