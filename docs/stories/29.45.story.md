## 💼 Valor de negócio

Em 2026-08-10 o gestor abriu o funil perpétuo, não encontrou os três gráficos por campanha/público/criativo, e reportou como *"os gráficos não apareceram"*. Não havia erro na tela, não havia aviso, não havia seção vazia — **não havia nada**. A pergunta que ele não tinha como responder sozinho era: o recurso não existe, quebrou, ou é o período que não tem dado?

As três respostas pedem ações opostas: chamar o time, tentar de novo, ou trocar o filtro. Uma tela que não distingue as três empurra toda ocorrência para o suporte.

Neste caso concreto a causa era a API do Railway rodando uma versão anterior à 29.42 — `/entity-daily` não existia ainda, a requisição voltou 404, e a seção inteira sumiu em silêncio.

---

## 🔍 Diagnóstico (verificado na `main`, 2026-08-10)

### O ponto exato

`perpetual-dashboard.tsx:348`, dentro de `EntityDimensionCharts`:

```ts
if (series.plotted.length === 0) return null;
```

`series.plotted` fica vazio para **três causas distintas** que o código colapsa numa só:

| Causa | Como chega aqui | Ação certa do gestor |
|---|---|---|
| Endpoint indisponível (404/500) | `useEntityDaily` rejeita → `entityDaily` é `undefined` → `rows: []` (`perpetual-dashboard.tsx:1556`) | avisar o time |
| Erro de rede / token | idem | tentar de novo |
| Período realmente sem dado | endpoint responde `200` com `rows: []` | trocar o período ou o filtro |

### O contrato do hook já perde a informação antes da tela

`perpetual-dashboard.tsx:1124` consome só duas das chaves que o React Query devolve:

```ts
const { data: entityDaily, isLoading: entityDailyLoading } = useEntityDaily(…);
```

`isError` e `error` são descartados ali. O componente recebe apenas `loading` (`perpetual-dashboard.tsx:277`) e, por construção, **não tem como** distinguir falha de vazio. O status HTTP existe e chega até esse ponto — `api-client.ts:43` anexa `err.status` ao erro lançado, então `error.status === 404` é observável.

### O padrão certo já existe neste mesmo arquivo

A 29.32 resolveu exatamente esta questão para os gráficos agregados, com o comentário explícito em `perpetual-dashboard.tsx:2161-2164`:

```
/* Story 29.32: mesmo padrão dos outros gráficos do arquivo — sem dado,
   mostra o EmptyState em vez de a seção sumir sem explicação. */
```

`EmptyState` (`perpetual-dashboard.tsx:3053`) é usado em quatro pontos do dashboard (`:2033`, `:2164`, `:2252`, `:2275`). A 29.42 é a única seção do arquivo que escapou desse padrão. **Esta story não inventa convenção nova — aplica a que o arquivo já tem** (IDS: REUSE).

### O que NÃO é o defeito

O aviso de cobertura parcial já existe e funciona: `semCobertura` (`perpetual-dashboard.tsx:380-385`) informa dias sem detalhamento por anúncio, e a série `(sem atribuição)` torna o resíduo visível. Esse caminho está correto e não deve ser tocado.

## 📖 Story

**Como** gestor de tráfego do funil perpétuo,
**quero** que a seção de gráficos por dimensão diga o que aconteceu quando não há gráfico para mostrar,
**para que** eu saiba se devo trocar o período, tentar de novo, ou avisar o time — sem abrir chamado para descobrir qual dos três.

---

## ✅ Critérios de aceite

### AC1 — O hook entrega o estado de erro à tela

`perpetual-dashboard.tsx:1124` passa a consumir `isError` e `error` de `useEntityDaily`, e `EntityDimensionCharts` (`perpetual-dashboard.tsx:275-287`) ganha as props correspondentes.

- O tipo do erro deve preservar `status` (`api-client.ts:43` já o anexa) — sem ele o AC3 é impossível.
- Nenhuma outra prop existente muda de significado.

### AC2 — Quatro estados, quatro renderizações distintas

| Estado | Condição | Renderiza |
|---|---|---|
| Carregando | `loading` | os 3 skeletons (comportamento atual, `perpetual-dashboard.tsx:341-347`) |
| Erro | `isError` | bloco de erro do AC3 |
| Sem dado | `!isError && series.plotted.length === 0` | `EmptyState` (reuso) |
| Normal | demais | os 3 gráficos (comportamento atual) |

**`return null` deixa de existir neste componente.** Nenhuma combinação de props pode produzir uma seção invisível.

### AC3 — O bloco de erro nomeia a causa e oferece a ação

Bloco em tom de erro (`border-red-500/30 bg-red-500/5`, o mesmo do aviso "Comparação indisponível" em `perpetual-dashboard.tsx:2520-2524` — reuso de convenção visual), contendo:

1. **404** → *"Este gráfico não existe na versão da API em uso. Avise o time — o painel está à frente do servidor."* Sem botão de retry: repetir a chamada não muda nada.
2. **Qualquer outro status ou falha de rede** → mensagem genérica de falha ao carregar **com** botão "Tentar novamente" ligado ao `refetch` do React Query.

O status HTTP aparece na tela em ambos os casos (ex.: `HTTP 500`). Sem ele, o relato do gestor volta como *"não apareceu"* e a investigação recomeça do zero — foi o que aconteceu em 2026-08-10.

### AC4 — O título da seção sobrevive a todos os estados

`"Evolução por {dimensão}"` (`perpetual-dashboard.tsx:353-355`) hoje está dentro do bloco que só renderiza no caminho feliz. Em erro e em vazio o título deve continuar visível.

Motivo: o gestor precisa saber que **a seção existe** para reportá-la. Uma área em branco sem rótulo não é reportável.

### AC5 — A decisão de estado é função pura, em `lib/utils`

**Corrigido na validação @po de 2026-08-10 — a versão anterior deste AC era inexequível.** `packages/web/vitest.config.ts:33` cobre **apenas** `lib/utils/**/*.test.ts`, em `environment: "node"`, sem `jsdom` e sem `@testing-library` — e isso é deliberado, documentado no cabeçalho daquele arquivo desde a 29.35. Um teste que monte `EntityDimensionCharts` não roda: viraria o 11º `.test.tsx` órfão do pacote.

Portanto o AC2 **não é decidido dentro do JSX**. A escolha do estado sai para uma função pura:

```ts
// packages/web/lib/utils/perpetual-entity-charts-state.ts
export type EntityChartsState =
  | { kind: "loading" }
  | { kind: "erro-versao" }              // 404 — sem retry
  | { kind: "erro"; status: number | null } // demais — com retry
  | { kind: "vazio" }
  | { kind: "ok" };

export function classifyEntityChartsState(input: {
  loading: boolean;
  isError: boolean;
  status: number | null | undefined;
  plottedCount: number;
}): EntityChartsState;
```

O componente vira um `switch` sobre o retorno. **Precedente direto no mesmo epic:** `classifyLpCoverage` (`perpetual-lp-rows.ts:202-223`) saiu do JSX pelo mesmíssimo motivo, três dias atrás — o comentário lá diz *"estava embutido no JSX, o que o tornava inalcançável por teste"*. Esta story segue a convenção, não cria uma.

Casos obrigatórios sobre a função pura:

1. `loading: true` → `loading`, **independentemente** de `isError` e de `plottedCount` (a precedência do AC2 é vinculante, e é o que evita o vermelho piscando)
2. `isError` com `status: 404` → `erro-versao`
3. `isError` com `status: 500` → `erro` com o status preservado
4. `isError` com `status: undefined` (erro fora do `api-client`) → `erro` com `status: null`, nunca `erro-versao`
5. sem erro e `plottedCount: 0` → `vazio`
6. sem erro e `plottedCount > 0` → `ok`

A renderização de cada `kind` (skeleton, bloco de erro, `EmptyState`, gráficos) é verificada **visualmente**, no DoD — é o mesmo contrato de verificação que o resto do dashboard já tem.

## 🚫 Fora de escopo

- **Corrigir a causa da ocorrência de 2026-08-10** — é deploy da API, não código. Esta story faz o sintoma ser legível, não o elimina.
- **Detectar a divergência de versão de forma sistêmica** — é a 29.46. Aqui o 404 é tratado como um status como outro qualquer.
- **A tabela "Desempenho por LP"** (`perpetual-dashboard.tsx:2491`, `{lpRows.length > 0 && …}`) tem o mesmo padrão de sumiço silencioso. Fica registrado; se voltar a incomodar, vira story própria. Ampliar aqui misturaria duas seções com fontes de dado diferentes na mesma revisão.
- **Retry automático / mudança de `staleTime`** — política de cache do React Query não muda nesta story.
