## 💼 Valor de negócio

O teste de LP é a decisão mais recorrente do perpétuo: qual página cortar, qual escalar. O dashboard já responde, na tabela **Desempenho por LP**.

O relatório — que é o que vai para a reunião e fica arquivado como retrato do período — não tem essa seção. Quem lê o relatório precisa abrir o dashboard ao lado, refiltrar o mesmo período e comparar de olho. E o relatório é um retrato: regerar depois dá número diferente, porque a planilha muda. A leitura do dashboard feita numa data não prova o que estava valendo na outra.

---

## 🔍 O que existe hoje (verificado na `main`, 2026-08-24)

**A regra de LP está pronta e testada, no lado errado do sistema.** Vive no web:

| Arquivo | O que faz |
|---|---|
| `web/lib/utils/lp-url.ts` | `normalizeLpUrl` — host sem `www`, query e fragmento fora, barra final fora, path preservado |
| `web/lib/utils/perpetual-lp-rows.ts` | `buildLpRows` — agrupa anúncios por LP, deriva métricas, mantém a invariante de soma |
| `api/routes/traffic-analytics.ts:773` | de onde vem `ad_id → linkUrl`, do `meta_ad_creatives_cache` |

O relatório roda inteiro na API e não alcança nenhuma das duas primeiras.

**As vendas já trazem o que é preciso.** `perpetual-report-metrics.ts:11` documenta a convenção: `utmContent` é o **ad ID**. O mesmo `ad_id` que o cache de criativos indexa. O caminho `venda → ad_id → linkUrl → LP` é o mesmo que o dashboard usa, com os mesmos dados.

Medição no `bbe-fc1-mai-26`, 17/07–23/08: **171 dos 196 anúncios (99,7% do investimento) têm LP resolvida**. A seção teria substância real desde o primeiro relatório.

---

## 📖 Story

**Como** gestor que leva o relatório para a reunião,
**quero** a seção de desempenho por landing page dentro dele,
**para que** a decisão de cortar ou escalar página esteja no mesmo documento que o resto, congelada no período.

---

## ✅ Critérios de aceite

### AC1 — A regra de normalização de URL é uma só, compartilhada

`normalizeLpUrl` vai para `packages/shared`, e web e API passam a importar de lá. Nenhuma cópia.

Duas implementações da mesma regra divergem no dia em que uma delas mudar, e o sintoma seria o pior possível: o relatório e o dashboard mostrando LPs diferentes para o mesmo período, sem nada indicando qual está certa.

> ⚠️ **Import do shared tem regra diferente por pacote neste projeto** (débito registrado na 19.14): o **web** importa por subpath; a **API** importa bare — subpath derruba o boot da API e ainda assim passa por `tsc`, `vitest` e `next build`. Errar aqui produz uma API que não sobe, com a suíte verde.

### AC2 — A seção sai do mesmo insumo da 29.58

O investimento por LP vem do spend por `ad_id` que a 29.58 traz ao loader, **já com o imposto por dia aplicado**. Nenhuma fonte nova, nenhuma chamada nova à Meta.

As URLs vêm de `meta_ad_creatives_cache` (`creative.linkUrl`), lidas do banco pelos `ad_id` do período — o mesmo `SELECT` que a rota `/ad-link-urls` faz.

### AC3 — Vendas e faturamento por LP, via `utm_content`

Cada venda paga com `utmContent` preenchido resolve para um `ad_id`, e dele para a LP. Vendas cujo `ad_id` não resolve para LP caem na linha do AC4, como o investimento.

A regra de comprador único da 29.53 vale aqui integralmente: **order bump não é venda nova**. A chave é `chaveDeComprador`, não a linha da planilha. Contar linhas infla a LP que vende o combo.

### AC4 — A linha "Sem link resolvido" entra também, e a soma fecha

A invariante do AC6 da 29.40 é o que dá confiança à tabela:

```
soma(investimento das linhas de LP, incluindo "Sem link resolvido")
  === soma(investimento dos anúncios que entraram)
```

Ela vale no relatório pelo mesmo motivo: uma seção que "quase bate" com o investimento total é indistinguível de erro de cálculo para quem lê — e no relatório o leitor não tem como conferir clicando.

### AC5 — Métricas por linha iguais às do dashboard

Investimento, Faturamento Bruto, Margem, Margem %, Vendas, CAC, ROAS — os mesmos nomes e a mesma ordem da tabela do dashboard.

Margem é **receita líquida − investimento** (decisão do Epic 29), com a taxa de plataforma que o relatório já resolve em `resolvePerpetualRates`. Faturamento e ROAS ficam brutos.

Duas telas para a mesma pergunta com rótulos diferentes é como a dúvida "esses dois números são a mesma coisa?" nasce.

### AC6 — Ausente ≠ zerado

Sem nenhuma LP resolvida — cache vazio, ou projeto sem sincronização de criativo — a seção **some** do relatório, como `formato`, `publicos` e `criativos` já fazem (§C.9). Não vai com uma linha "Sem link resolvido" de 100% e todas as outras vazias.

E some com um alerta declarando por quê. Sumir em silêncio faria o leitor achar que o relatório é de uma versão anterior.

### AC7 — Ordenação por investimento, com a linha não resolvida no fim

Mesma regra de `perpetual-lp-rows.ts:166`: ordena o conjunto inteiro por investimento decrescente e empurra "Sem link resolvido" para a última posição, **independente do valor dela**.

Ela não é uma LP; deixá-la competir no ranking colocaria no topo uma linha sobre a qual não há nenhuma ação possível.

## 🧪 Verificação por reversão (obrigatória)

| Reversão | Teste que deve falhar |
|---|---|
| a API volta a ter cópia própria de `normalizeLpUrl` | duas URLs que o web funde aparecem como LPs distintas no relatório |
| a linha "Sem link resolvido" sai | a soma da seção fica abaixo do investimento total sem nada declarar |
| a dedup de comprador do AC3 sai | uma venda com order bump conta 2 na LP |
| a seção passa a renderizar vazia em vez de sumir (AC6) | relatório sem cache de criativo sai com uma seção 100% não resolvida |
| a ordenação passa a paginar antes de ordenar | a LP de maior investimento não é a primeira |
| "Sem link resolvido" volta a competir no ranking | ela aparece no topo quando tem o maior investimento |
| o import do shared vira subpath na API | a API não sobe — e `tsc`, `vitest` e `next build` continuam verdes |

⚠️ O último caso **não é pego por nenhum gate automático**. Precisa de uma verificação de boot real, não de compilação.

---

## 🚫 Fora de escopo

- **Resolver LP que o cache não tem.** É a 29.56 (auto-cura). Aqui a linha não resolvida é declarada, não caçada.
- **Link clicável na LP dentro do relatório.** O HTML é arquivado e pode ser aberto muito depois; decidir sobre link externo em documento arquivado é escopo próprio.
- **Comparativo de LPs entre períodos.** O relatório é retrato de um período.
- **Mover `buildLpRows` inteiro para o shared.** Só `normalizeLpUrl` é a regra compartilhada. A agregação do relatório tem colunas e dedup de comprador próprios — forçar uma função para os dois lados acoplaria duas apresentações diferentes.
