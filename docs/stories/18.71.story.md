### A conta do relato fecha exatamente

Aba `n8n-Kiwify` do funil `bbe-pr2-ago-26`, etapa Captação Paga:

```
s=meta → co= em JSON = 2      ← somem da tabela
s=meta → co= id puro  = 4      ← é o que a tela mostra hoje
                        ---

```

As duas que somem:

```
2026-08-28  antonio leonardo  R$ 2.194,00  co={"co":"120247542282230489","url":"lps.netaobombeef.com/bbepr2-captura-a/","v":1}
```

### ⚠️ Correção do @qa: não é um formato com variações — são três formatos

A v1 desta story afirmava que o `co=` sempre chega como `{co, u?, url, v}`. **Não
chega.** Rodando `JSON.parse` sobre as 85 células que começam com `{`, em todas
as abas de venda de produção:

```
começam com "{"   : 85
parseiam como JSON:  5   ←  o formato que a story descrevia
FALHAM no parse   : 80
```

Os três formatos, e onde cada um está:

| # | formato | linhas | onde |
|---|---|---|---|
| 1 | `{"co":"1202…","url":"…","v":1}` — objeto válido | **5** | só `bbe-pr2-ago-26` |
| 2 | `{"org","org"}`, `{"imersao","imersao"}` — par duplicado, **não é JSON** | **41** | `fz-l2-jun-26`, `fz-m2-jul26`, `dg-pg02` |
| 3 | `{{ad.id}}` — macro do Meta **não resolvida** | **42** | `dg-pg02` (39), `dg-pg04` (2), `fz-m2-jul26` (1) |

O que isso muda:

- ✅ **O caso do relato continua resolvido.** As 2 vendas do `bbe-pr2`
  (R$ 2.991,00) são formato 1 — o AC1 as recupera, e o AC3/AC4 fecham.
- ❌ **"9 abas em 5 funis" é otimista.** Só **1 aba, 1 funil** tem o formato que
  o AC1 corrige. As outras 8 têm formatos 2 e 3, que a regra "JSON inválido volta
  como texto cru" deixaria passar exatamente como hoje.
- ❌ **O AC6 estava errado** e foi reescrito. Os `{"org","org"}` — a maioria dos
  casos orgânicos — são formato 2 e **não** virariam `org` pela AC1 sozinha.
- ℹ️ O formato 3 **não é problema de parsing**: é anúncio publicado com a macro
  do Meta sem substituir. `survey-aggregation.ts` já o barra via `isLikelyAdId()`.
  Corrigir a origem é trabalho de tráfego, não de código.

## 🐛 Por que a venda some

O código trata o `co=` como texto e só tira o `_` que o Sheets prefixa em número:

```ts
// packages/api/src/utils/creative-sales-metrics.ts:59  (idêntico em stage-creative-performance.ts:187,
//                                                       creative-revenue.ts:65, survey-aggregation.ts:74)
function normalizeNumericId(id: string): string {
  const trimmed = id.trim();
  if (trimmed.startsWith("_")) { const rest = trimmed.slice(1); if (/^\d+$/.test(rest)) return rest; }
  return trimmed;   // ← devolve a string JSON inteira
}
```

Com o JSON inteiro como chave, os dois consumidores falham em silêncio:

**Tabela de LPs** — a chave não acha campanha, e a função retorna sem somar:

```ts
// packages/api/src/routes/stage-creative-performance.ts:502
const attributeSaleToLp = (adId: string, value: number) => {
  const campaignName = campaignByAdId.get(adId);
  if (!campaignName) return;        // ← a venda evapora aqui, sem log
  …
};
```

**Tabela de Criativos** — `computeCreativeSalesMetrics` conta a venda, mas numa
chave (`{"co":"1202…}`) que não corresponde a nenhum anúncio da Meta; a linha
nunca é renderizada.

Nos dois casos **não há erro**: a venda simplesmente não aparece. É o padrão de
[erro virando ausência na tela] que já pegou o time três vezes.

O `sanitizeUtmValue` de `stage-sales-data.ts:573` (cards do topo) também deixa o
JSON passar cru — lá o efeito é um grupo "Não informado" a mais, não uma perda.

## 🎯 Acceptance Criteria

### AC1 — Um normalizador único, com teste, para o `co=` em JSON
Criar um helper compartilhado (sugestão: `packages/api/src/utils/utm-value.ts`)
que receba o valor cru da célula e devolva o `utm_content` efetivo:

| Entrada | Saída |
|---|---|
| `120247234266910489` | `120247234266910489` |
| `_120247234266910489` | `120247234266910489` (comportamento atual preservado) |
| `{"co":"120247542282230489","url":"…","v":1}` | `120247542282230489` |
| `{"co":"org","u":"…","url":"…","v":1}` | `org` |
| `{"co":"link_in_bio","url":"…","v":1}` | `link_in_bio` |
| `{"url":"…","v":1}` (sem `co`) | `""` |
| `{"org","org"}` (formato 2) | `org` |
| `{"imersao","imersao"}` (formato 2) | `imersao` |
| `{"a","b"}` (par não duplicado) | o texto cru — não adivinhar qual vale |
| `{{ad.id}}` (formato 3, macro não resolvida) | `""` — não é criativo |
| `{ qualquer outra coisa` | o texto cru (não pode lançar) |
| `""` / `"   "` | `""` |

O parse **não pode lançar** em nenhuma entrada: célula de planilha é dado
externo. JSON inválido volta como texto cru.

### AC2 — Os quatro `normalizeNumericId` passam a usar o normalizador
`creative-sales-metrics.ts:59`, `stage-creative-performance.ts:187` e
`creative-revenue.ts:65` são **byte a byte a mesma função**;
`survey-aggregation.ts:74` é equivalente, escrita em uma linha. Os quatro passam
a delegar ao helper do AC1 — sem quatro correções divergentes.

⚠️ **`survey-aggregation.ts` tem um filtro que não pode se perder.** Logo abaixo
do `normalizeNumericId` ele define `isLikelyAdId()`, que mantém fora do `byAdId`
o que não é criativo — rótulo agregado (`org`, `link_in_bio`) e macro não
resolvida (`{{ad.id}}`). Com o AC1, um `co=` em JSON passa a devolver `org` em
vez da string JSON, e esse filtro **passa a receber exatamente o que ele existe
para barrar**. Trocar o normalizador ali sem reler o `isLikelyAdId` muda o que
entra no `byAdId`. Conferir antes e depois.

### AC3 — A tabela de LPs mostra 6 vendas para a LPA
Com o funil `bbe-pr2-ago-26` / Captação Paga e a janela que cobre agosto,
**Desempenho de Testes de LPs** mostra **6** ingressos na LPA, não 4. As duas
vendas que entram são as de 28/08 (R$ 2.194,00) e 30/08 (R$ 797,00).

### AC4 — A tabela de Criativos mostra as mesmas 6
**Desempenho de Criativos** soma **6** vendas nos criativos da LPA, e as duas
recuperadas caem nos anúncios `120247542282230489` e `120247234209500489` —
não numa linha "—" nem num grupo novo.

### AC5b — Nenhuma regressão no filtro do `byAdId`
Depois do AC2, `survey-aggregation.ts` passa a receber `org`/`link_in_bio` onde
antes recebia texto cru. Conferir que `isLikelyAdId()` continua barrando os três
formatos, e que o conteúdo do `byAdId` não muda nas abas sem formato 1.

### AC5 — Teste diferencial: reverter o fix derruba o teste
O teste do AC1 precisa **falhar** se `normalizeNumericId` voltar ao corpo atual.
Um teste que passa nos dois estados não prova nada — foi o que a
[reversão para provar o teste] cobrou na 44.2. Incluir um caso de ponta a ponta
com uma linha em JSON: com o fix, a venda é atribuída ao ad_id; sem ele, não é.

### AC6 — O valor orgânico volta legível, nos **dois** formatos
Na dimensão **Ad Name** da tabela "Leads & vendas por UTM", uma venda agrupa em
`org` tanto vindo de `{"co":"org",…}` (formato 1) quanto de `{"org","org"}`
(formato 2) — não numa célula com o texto cru.

Este AC só é verificável nas abas que têm formato 2 (`fz-l2-jun-26`,
`fz-m2-jul26`, `dg-pg02`); o `bbe-pr2` **não serve** para testá-lo.

⚠️ Hoje cada `{"co":"org","u":"<uuid>",…}` é um grupo **distinto** na tela,
porque o `u` muda a cada venda. Depois do fix elas colapsam num único `org` — a
contagem de grupos cai, e isso é o resultado correto, não uma perda.

(A tabela também não enxerga as vendas dessa etapa; isso é a **18.72**, e as
duas correções são independentes.)

## 🚫 Fora de escopo

- **Usar o `url` de dentro do JSON para resolver a LP.** O payload traz a URL de
  destino, o que resolveria a LP sem passar pela campanha. É uma mudança de
  regra de atribuição, não um bug — vale uma story própria.
- **Mudar o n8n para voltar a gravar o id puro.** O app tem que ler o que a
  planilha entrega; o formato é de quem escreve nela.
- **Backfill.** As leituras são ao vivo sobre a planilha; não há dado derivado
  persistido para corrigir.
- **`sanitizeUtmValue` do perpétuo** (`perpetual-sales-data.ts:65`). Mesmo
  formato, mas outro dashboard e outro conjunto de abas — medir antes.
