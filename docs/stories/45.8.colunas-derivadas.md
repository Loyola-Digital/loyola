# Story 45.8 — Colunas derivadas entre queries

**Epic:** 45 — Construtor de BI
**Status:** Done
**Priority:** Medium
**Estimate:** M
**Depends on:** 45.7

---

## Story

Como quem monta o painel, quero um widget que **combine duas consultas com escopos diferentes** — por exemplo receita de tudo menos gasto de uma campanha — sem escrever SQL.

## Contexto

O dossiê chama isto de "a joia" da DSL, e a razão é específica: **cada `querySpec` pode ter filtros diferentes**. É o que permite "lucro" com escopos assimétricos.

```ts
querySpecs: [
  { metrics: ["revenue"], filters: { date: {...} } },                          // q0
  { metrics: ["spend"],   filters: { date: {...}, campaign: { $like: "%a1%" } } }, // q1
],
derivedColumns: [
  { name: "lucro", expression: "q0.revenue - q1.spend", mode: "scalar", semanticType: "currency" },
],
```

## Contexto Técnico

### ⚠️ O parser (regra não-negociável 4)

A expressão é **código do usuário rodando no nosso servidor**. Avaliada por parser recursivo escrito à mão — **nunca `eval`, nunca `new Function`**, nem "só no cliente".

Gramática mínima: `+ - * /`, parênteses, número literal, referência `qN.coluna`. Divisão por zero → `null` (regra 1), não `Infinity`.

### `mode`

`scalar` = um valor para o widget inteiro. `row` = calcula por linha, e aí as queries precisam de `mergeKey` para casar as linhas.

### Auto-split (o que o dossiê manda copiar sem pensar muito)

Quando a pessoa adiciona no editor uma métrica de **outra entidade**, o sistema cria a segunda `querySpec` sozinho e define o `mergeKey` — *"é o que torna multi-entidade usável sem UI de join"*.

## Critérios de aceitação

**AC1** — Parser próprio, sem `eval`/`new Function`, com teste que prova que expressão maliciosa não executa.

**AC2** — `+ - * /`, parênteses e precedência corretos.

**AC3** — Divisão por zero e referência a query inexistente → `null` com aviso, nunca exceção que derruba o dashboard.

**AC4** — `mode: "row"` casa linhas por `mergeKey`; linha sem par vira `null` naquela coluna.

**AC5** — Auto-split ao adicionar métrica de outra entidade, com o `mergeKey` escolhido automaticamente e **mostrado** na tela.

**AC6** — Limite de 4 `querySpecs` e 10 colunas derivadas por widget.

### A gramatica e uma lista do que se ACEITA

Dez expressoes de ataque viraram teste — `process.exit(1)`,
`constructor.constructor('return process')()`, `require('fs')...`, template
string com `process.env`. Nenhuma delas precisou de regra propria para ser
barrada: o tokenizador so conhece numero, `qN.coluna`, quatro operadores e
parenteses, e tudo o mais e erro de analise. Lista fechada do que entra, nao
lista aberta do que se proibe.

Dois erros que poderiam passar em silencio viraram recusa explicita: sobra
depois do fim (`q0.a q1.b` devolveria 100 — o valor da primeira metade, com cara
de total) e parentese sem fechar.

### `null` contamina, e e o certo

Divisao por zero devolve `null`, nunca `Infinity` — infinito propaga por toda
soma e ordenacao a partir dali. E qualquer operando `null` faz a conta inteira
ser `null`: se um pedaco nao tem amostra, o resultado nao tem valor.

Ha uma distincao que o teste guarda: **referencia quebrada** (`q7.x` num widget
de duas consultas) gera aviso, enquanto **dado ausente** (`q0.vazio`) nao —
o primeiro e erro da expressao, o segundo e ausencia de medicao.

### Merge entre entidades precisa de traducao de chave

O caso que motiva a story cruza entidades, e `trafego.date` e `vendas.date` sao a
mesma coisa com nomes diferentes. O indice de cada consulta usa **a coluna dela**,
achada pelo sufixo — sem isso, o merge entre entidades nunca casaria nenhuma
linha e a coluna viria vazia, calada.

### A validacao roda na ESCRITA

Uma expressao apontando para `q3` num widget de duas consultas e recusada no
`PUT`, nao so ignorada na leitura. Senao viraria coluna vazia todo dia, sem
ninguem saber por que.
