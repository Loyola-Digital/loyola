## 🧭 A causa: deploy da API ≠ bundle do MCP

São dois artefatos diferentes, e é fácil confundi-los — **este documento existe porque alguém confundiu**, em 28/08, e disse ao dono do produto que "merge = tools no ar".

| Artefato | O que é | Como atualiza |
|---|---|---|
| **A rota** (`/api/public/...`) | endpoint da API | **automático** — merge na `main` dispara o deploy |
| **A tool MCP** (`get_*`) | processo **stdio** local ao gateway (`packages/mcp/src/index.ts:20`, `StdioServerTransport`) | **manual** — rebuild do bundle + restart no gateway |

O MCP **não é um serviço deployado**. É um binário (`bin: loyola-x-mcp` → `dist/index.js`) executado pela máquina que hospeda o agente. Nenhum passo do pipeline da `main` toca nele.

O `docs/guides/mcp-inacio-integracao.md:31` já dizia isso em **julho** — *"As 2 tools novas exigem o bundle MCP atualizado no teu gateway (Lucas providencia)"*. A frase estava certa e a atualização não aconteceu. Uma instrução em prosa, dentro de um doc de 500 linhas, não é um mecanismo.

## ✅ Fechamento (2026-09-08, @devops — Gage)

A leva do Inácio somou a tool `get_perpetual_metrics` (Story 44.29) e **a
recorrência aconteceu no mesmo dia**: mergeada, gateway atrás no mesmo instante.
Foi o que motivou fechar as ACs que faltavam.

### AC2 — já estava pronta, e foi VERIFICADA

`packages/mcp/src/defasagem.ts` busca `/api/public/v1/mcp-manifest`, compara com
o que o próprio bundle registrou e publica um aviso no roster. Não estava
provado que funcionava. Provado em 08/09, contra o manifesto de produção:

```
cenário: gateway com o bundle de ontem (18 tools) × main com 19
  atrasado: true
  faltando: get_perpetual_metrics
  mensagem: "Este gateway serve 18 tools; a main tem 19. FALTAM 1: ..."

controle: gateway em dia
  atrasado: false   ✅
```

O controle importa: um detector que acusa sempre não distingue nada.

### AC3 — o gatilho, pela saída (b)

Job `avisar-gateway-mcp` em `.github/workflows/ci.yml`. Quando a PR toca
`packages/mcp/**` ou `packages/shared/src/mcp-tools.ts`, o CI **comenta na PR**
com o passo a passo do rebuild.

**Por que comentário e não check que falha:** o bundle desatualizado não é
defeito do código da PR — o código está certo. Falhar o CI ensinaria o time a
ignorar um vermelho legítimo, que é o mesmo raciocínio do `continue-on-error`
que já existe no job de teste.

**Por que não bastava o detector do MCP:** ele avisa **ao agente**, na próxima
execução. Quem mergeia não fica sabendo — e é quem pode agir.

#### Verificado EM EXECUÇÃO, não só na lógica

A detecção foi conferida contra o diff de PRs reais (#808 dispara, #816 e #809
silenciam). Mas isso prova a regra, não o gatilho: um job pode passar verde sem
postar nada, e aí o aviso estaria escrito e morto.

Provado ponta a ponta na própria PR #817, com commits temporários depois
revertidos:

| o que se provou | como | resultado |
|---|---|---|
| **dispara** | commit tocando `packages/mcp/src/tools.ts` | ✅ comentário postado, markdown íntegro |
| **não repete** | segundo commit no mesmo arquivo | ✅ seguiu em 1 comentário |
| **silencia** | a PR sem tocar o MCP | ✅ job passa sem postar |

⚠️ **Um quase-falso-positivo, que vale registrar.** A primeira verificação
procurou a string solta `aviso-gateway-mcp` nos comentários e achou **dois** —
o segundo era o comentário do Vercel, porque o nome da branch aparece na URL de
preview. O job usa o marcador completo `<!-- aviso-gateway-mcp -->`, que não
tem esse problema; quem estava frouxa era a checagem, não a guarda. Com o
marcador exato: 1.

#### O erro que este job cometeu contra si mesmo

A primeira versão derrubou a própria PR: `actions/checkout` falhou com
*"Repository not found"*. **Declarar `permissions:` num job substitui o conjunto
inteiro** — pedir só `pull-requests: write` tirou o `contents: read`.

A correção não foi acrescentar a permissão: foi **remover o checkout**. A
pergunta é "quais arquivos esta PR mudou", e `gh pr diff --name-only` responde
sem clonar nada — o `git diff` trazia junto profundidade de clone, merge-base e
permissão, três modos de falha para uma pergunta que a API responde direto.
